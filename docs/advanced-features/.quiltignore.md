# .quiltignore

`.quiltignore` keeps files out of a package. Put it at the top of the package
folder, one rule per line, in the [`.gitignore`
syntax](https://git-scm.com/docs/gitignore). This is useful when, for example,
your data and your code live in the same folder.

QuiltSync and the `quilt` CLI apply the full rule set described below. quilt3
reads only the folder's own `.quiltignore`, and reads it in a simpler way: see
[quilt3](#quilt3).

## QuiltSync and the `quilt` CLI

### Three layers of rules

A path is checked against three layers, weakest first:

1. **Built-in rules**: a fixed list of clutter, secrets and caches that ships
   with the app. See [Built-in rules](#built-in-rules).
2. **Your rules**: a `.quiltignore` in the app's data folder. It applies to
   every package on your computer and is not shared with anyone:
   - macOS: `~/Library/Application Support/com.quiltdata.quilt-sync/.quiltignore`
   - Windows: `%LOCALAPPDATA%\com.quiltdata.quilt-sync\.quiltignore`
   - Linux: `~/.local/share/com.quiltdata.quilt-sync/.quiltignore`

   QuiltSync and the `quilt` CLI share this file. If you pass the CLI a
   different domain folder (`--domain` or `QUILT_DOMAIN`), it reads
   `.quiltignore` from that folder instead.
3. **This package's .quiltignore**: the file at the top of the package folder.
   It travels with the package, so everyone who installs the package gets it.

All three use `.gitignore` syntax. A path in your rules file is relative to
the package folder, so `/build/` means a `build` folder at the top of every
package.

### How a path is decided

- **The last matching line wins.** Within one file, a later line overrides an
  earlier one.
- **A stronger layer wins.** The package's file overrides your rules, and your
  rules override the built-in rules.
- **A `!` line brings a path back.** `!.env.example` in your rules file keeps
  `.env.example` in packages even though the built-in rule `.env.*` matches it.
- **A folder's contents are decided one level at a time, as in git.** A path is
  checked from its top folder down. If a folder is ignored, everything in it is
  ignored. If a `!` line brings a folder back, each file in it is still checked
  on its own, so files that a rule names stay out.

For example, the built-in rules ignore every folder whose name starts with a dot
and every `*.pem` file. A user adds this line to the package's `.quiltignore`:

```gitignore
!/.config/
```

Now `.config/settings.json` goes into the package, but `.config/server.pem`
stays out, because the built-in `*.pem` rule still matches it.

### Which files each layer can leave out

- **Built-in rules and your rules hide new files only.** A file the package
  already has stays in the package, even if it matches. Your personal rules
  never change what is in a package that others share.
- **This package's .quiltignore also leaves out files the package already
  has.** If a line matches a file in the package, the next commit leaves the
  file out.

Built-in rules and your rules never hide the package's own top-level
`.quiltignore`. A line in that file can still hide it.

### Built-in rules

The built-in rules keep out files that are almost never data. They come in
these groups:

- **Hidden folders**: any folder whose name starts with a dot, such as `.git`,
  `.venv` or `.ipynb_checkpoints`. Hidden *files* are not in this group, so
  data such as Zarr's `.zattrs` and `.zarray` stays in.
- **macOS**: `.DS_Store`, `._*` and other Finder files.
- **Windows**: `Thumbs.db`, `desktop.ini`, `$RECYCLE.BIN/` and similar.
- **Linux and network drives**: `.directory`, `.nfs*`.
- **Editors and office lock files**: `~$*`, `*.swp`, `*~`, `*.code-workspace`
  and similar.
- **Secrets**: `.env`, `.env.*`, `.netrc`, `*.pem`.
- **Python and Node**: `__pycache__/`, `*.py[cod]`, `node_modules/`.

Built-in rules match regardless of case, so `.DS_Store` also matches
`.ds_store`. Lines in your rules and in a package's `.quiltignore` match case
exactly.

To see every built-in rule, turn on **New design preview**, open **Settings**,
find the **Ignore rules** card and click **Review…** next to **Built-in
rules**. To let a rule's new files in, turn its box off and click **Confirm**.
QuiltSync writes `!` and the rule, such as `!*.pem`, to your rules file.
Turning the box back on removes that line.

### Stop ignoring

With **New design preview** on, each ignored file or folder on a package page
names the rule that hid it and where the rule came from: *Built-in rule*,
*Your rules, line 4* or *This package's .quiltignore, line 2*.

Choose **Stop ignoring** on the row to bring it back. The popup asks where to
write the `!` line:

- **This package** (the default): adds a line anchored to the path, such as
  `!/.snakemake/`, to this package's `.quiltignore`. It travels with the
  package.
- **All packages**: adds a line with the name only, such as `!.snakemake/`, to
  your rules file. It is personal. It is offered only when no line in the
  package's `.quiltignore` hides the path, since your rules can't override the
  package's file.

Before it writes, the popup says what will move, for example: "This adds 5,412
files (210 MB) to the package on the next sync." If a folder above the path is
ignored too, the popup adds a `!` line for that folder as well.

### `quilt status`

`quilt status` ends with how many files and folders the rules leave out:

```text
3 ignored files and 1 ignored folder not included (list them with --ignored)
```

`quilt status --ignored` lists each ignored path with its rule and where the
rule came from: `built-in`, your rules file and line, or `.quiltignore` and
line. With `--format json`, each path has a `source` field (`built-in`, `user`
or `package`) and, for a rules file, its `line`.

```bash
quilt status --ignored
```

## quilt3

`quilt3.Package.set_dir` reads only the `.quiltignore` at the top of the folder
it packages. It does not apply the built-in rules or your rules file, so the
same folder packaged with quilt3 and with QuiltSync can differ.

quilt3 matches each line as a shell-style wildcard (Python's `fnmatch`)
against the end of each path. It does not support `!` lines, comments or
anchored lines such as `/build/`, and `*` can match across folders.

```bash
$ ls
foo.txt         bar.txt         baz.txt
$ python -c "import quilt3; print(quilt3.Package().set_dir('/', './'))"
(local Package)
 └─foo.txt
 └─bar.txt
 └─baz.txt
$ echo foo.txt >> .quiltignore
$ ls -a
foo.txt         bar.txt         baz.txt
.quiltignore
$ python -c "import quilt3; print(quilt3.Package().set_dir('/', './'))"
(local Package)
 └─bar.txt
 └─baz.txt
 └─.quiltignore
```
